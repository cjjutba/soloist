# Story 5.2: Send Invoice + Client View + Manual Status

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Freelancer,
I want to send a Draft Invoice and track its status,
so that my client can see it in their portal and I can mark it paid (FR-18, UX-DR12).

## Acceptance Criteria

1. **Send a Draft → Sent, fanning out through the Epic 4 notification seam (FR-18, AR-9/AR-11, UX-DR12).**
   **Given** a Draft Invoice on its Cockpit document view
   **When** I send it
   **Then** its `status` transitions **`draft → sent`** atomically (a server-side guard — only a `draft` can be sent; a re-send is a no-op, never a second event), an **`invoice.sent`** Inngest event fires, and that event fans out through the **existing Story 4.4 `resolveNotifiableRecipient` gate** → an **in-app `invoice_sent` notification** (carrying the new `invoice_id`) **+ a branded email** (the shared `EmailShell`) **+ the 4.2 toast-if-active** — all **respecting the per-Client mute preference** (muted = no row, no email, no toast; the Client can still open the invoice from the portal). The status enum is **`draft | sent | paid` ONLY**; there is **no payment processing** anywhere in the product.

2. **The Client views the Invoice in-portal as a premium document; Drafts never leak (FR-18, UX-DR12, NFR-2).**
   **Given** a Sent (or Paid) Invoice
   **When** the Client opens the portal **Documents** area
   **Then** they see a list of **their** Invoices (number · status chip · total in the `numeric` token · dates) and can open one as the **premium read-only document** — the **same `InvoiceDocument`** render the Cockpit uses (serif feel, Tenant brand "from", `numeric` money, status chip). A **`draft` Invoice is NEVER visible to the Client** (the portal read is status-bounded at the repository — a draft is Freelancer-only until sent). The notification center's `invoice_sent` entry **links to this in-portal Invoice** with an invoice label. This view is the foundation Story 5.3's Download/PDF builds on.

3. **A Freelancer marks a Sent Invoice Paid manually — out-of-band, no processing (FR-18, §11).**
   **Given** a Sent Invoice
   **When** the client pays me out-of-band and I mark it Paid
   **Then** its `status` transitions **`sent → paid`** (a server-side guard — only a `sent` can be marked paid; a `draft` cannot skip to `paid`), and that is the terminal status. Paid is a **manual** Freelancer action with **no notification/email** (the AC scopes the fan-out to `invoice.sent` only) and **no payment integration** of any kind.

### The load-bearing decisions (calls made for this story)

[Source: epics.md#Story 5.2 AC (the contract); the autonomous Epic 5 brief; 5.1 Dev Notes]

1. **Scope = Send + Client view + Manual Paid ONLY — no draft-edit surface.** The epics.md 5.2 AC is exactly "send → Sent + `invoice.sent` + Client in-portal view" and "mark Paid manually; transitions Draft→Sent→Paid only." It says **nothing about editing a draft**, and FR-18 is "delivery & manual status," not editing. 5.1's passing aside ("editing lands with 5.2") is **not** in the 5.2 AC. Per the project's repeated YAGNI lesson (the 4.4 over-engineering retro) and to avoid scope-creep, **5.2 does NOT build a draft editor** — the Freelancer reviews the existing read-only document, then Sends; a wrong draft is re-created (v1). (If editing is later wanted, it's its own story.)
2. **Paid fires no notification/email.** The AC fans out **only** `invoice.sent`. Marking Paid is the Freelancer's private out-of-band bookkeeping flip — no Client ping. (Keeps the seam honest: one event, one fan-out.)
3. **Drafts are Freelancer-only; the Client read is status-bounded at the repository.** `invoice_scope` RLS for a Client (engagement ctx) returns **all** of their engagement's invoices, **including drafts** — so the draft-exclusion MUST live in the query (`listClientInvoices`/`getClientInvoice` filter `status <> 'draft'`), exactly like `ship_updates`' published-only Client read. This is the privacy boundary; not the UI's job alone.
4. **Atomic status transitions via a guarded UPDATE — not read-then-write.** `markInvoiceSent` is `UPDATE … WHERE id AND status='draft' RETURNING`; only a real transition returns a row, so the action emits **exactly one** `invoice.sent` even under a double-click/concurrent send. Same for `markInvoicePaid` (`status='sent'`). The pre-`getInvoice` read is for friendly errors + the URL-tamper engagement cross-check, NOT the concurrency guarantee.
5. **The `invoice.sent` enqueue is best-effort (post-commit), like publish.** The status write is the durable truth; if `inngest.send` throws, log + Sentry and return `{ok:true}` — the Client still sees the invoice in the portal; only the ping is missed. (Opposite of the webhook's record-before-enqueue compensation — there the DB write must not outlive a failed enqueue; here it must.)

### The load-bearing implementation details

[Source: schema.ts (notifications L354-386, invoices L396-431); the 5.1 guard lesson; `handleShipPublished`; architecture.md L297]

- **The `getInvoice` ownership + engagement cross-check is load-bearing.** `invoice_scope`'s WITH CHECK/USING reduces to `tenant_id` for a freelancer ctx (no `app.engagement_id` GUC), so an UPDATE by id alone could touch another of the caller's engagements' invoices (harmless but wrong revalidate) — and a tampered `engagementId` in the action input must not mis-target. `getInvoice(ctx,id)` (RLS-scoped → null if not theirs) + `invoice.engagementId !== engagementId ⇒ bail` is the same defense as the 5.1 `[invoiceId]` page's `engagementId !== id` check.
- **`invoice_id` is nullable, FK, ON DELETE cascade — and rides the existing policy.** The `notification_scope` dual-scope policy + FORCE already exist (0012); ADD COLUMN doesn't disable RLS, so **no policy/FORCE work** in 0015 — just the column + FK + the partial unique. The two partial uniques (`…_ship_dedup` on `(user_id, ship_update_id) WHERE ship_update_id IS NOT NULL`, `…_invoice_dedup` on `(user_id, invoice_id) WHERE invoice_id IS NOT NULL`) are disjoint (a row has at most one of the two ids), so bare `onConflictDoNothing()` can only ever fire as the intended dedup.
- **Fan-out idempotency mirrors ship-published.** A whole-function Inngest retry: the notification insert dedupes (the invoice partial unique → null on the 2nd), the email may resend (a benign duplicate). If `loadInvoiceSentContext` shows the invoice no longer `sent` (a race), keep the notification + skip the email (`{status:"stale"}`), exactly like the dismissed/edited ship race. Re-read fresh — never trust event-carried content.
- **Money: integer minor units everywhere, `formatMoney` only.** The email and both UI surfaces render `amountTotal`/line amounts via `formatMoney(minor, currency)` (the existing helper, with its try/catch + per-currency fraction digits). No float math, no hand-rolled `Intl.NumberFormat`, no re-derived `÷100`.
- **The portal `[invoiceId]` reads Tenant brand under a Client ctx.** `getTenant(session)`/`getBranding(session)` are `tenant_id`-scoped (the `tenant_self`/`branding_tenant` policies); a Client ctx sets `app.tenant_id`, so these resolve the Client's own Tenant brand (the portal shell already does this for the logo). The accent on a **client-facing** document is correct (it's the Freelancer's brand as the "from").

## Senior Developer Review (AI)

**Reviewer:** CJ (via Claude adversarial review — 3 parallel layers: Blind Hunter, Edge Case Hunter, Acceptance Auditor) · **Date:** 2026-06-10 · **Outcome:** ✅ Approve (1 Med fix applied; the load-bearing logic was clean)

**Scope:** Blind Hunter (diff only — logic/concurrency/money/security), Edge Case Hunter (diff + repo — every branch/boundary vs the `handleShipPublished` sibling), Acceptance Auditor (diff + spec + the non-negotiables).

**Headline: the high-risk logic is correct.** All three layers independently confirmed — the status transitions are atomic guarded UPDATEs (exactly one `invoice.sent` under a double-send; Draft can't skip to Paid); the two partial uniques are disjoint so the bare `onConflictDoNothing` only ever fires as the intended dedup; **drafts cannot leak to the Client** via the list, the detail page, or a notification (status-bounded at the repository, defense-in-depth); the `getInvoice` + `engagementId` cross-check scopes both status actions (the load-bearing tamper guard, since `invoice_scope`'s WITH CHECK only gates `tenant_id` for a freelancer ctx); money is integer-minor-unit via `formatMoney` everywhere (email included); the fan-out rides the Story 4.4 mute gate with no duplicated pref logic; the `invoice_id` column rides the existing `notification_scope` (isolation `ap/aq`); AR-14 boundaries + the shared `EmailShell` + the a11y floor + the `InvoiceDocument` reuse are all honored.

**Findings (1 actioned, the rest dismissed as by-design):**

1. **[Med — FIXED] The email was suppressed when a Sent invoice was marked Paid before the async fan-out ran.** `handleInvoiceSent` gated the email on `ctx.status !== "sent"` — a faithful-but-imperfect mirror of `handleShipPublished` (where `published` is terminal). An invoice's `sent` is NOT terminal: a freelancer can mark it Paid within the fan-out's queue window, and the gate would then return `stale` → the client got the in-app notification but **no email**. **Fix:** skip only when the invoice is gone or still `draft` (`!ctx || ctx.status === "draft"`); `sent` OR `paid` both send the email (both mean it was legitimately sent). Added a `paid`-context test asserting the email still fires.
2. **[Low — dismissed, by-design] Email may re-send on an Inngest whole-function retry.** Identical to `handleShipPublished` (idempotency is the notification dedup; the email is intentionally NOT gated on the first-insert so a failed email can RETRY and recover — NFR-4). Gating the email on a newly-created notification would break retry-recovery. Documented trade-off, consistent with the codebase.
3. **[Low — dismissed, by-design] Notification is created before the stale re-read.** Mirrors `handleShipPublished` ("the notification records the moment"); the FK `ON DELETE cascade` self-heals a dead link, and no code path deletes a sent invoice today (latent only).
4. **[Low — dismissed, v1 scope] `issuedAt` reflects draft-creation, not send time.** `issuedAt` is freelancer-controlled at creation (the 5.1 builder's issue-date field); overriding it on send would discard their chosen date, and there is no edit surface by design (5.2 scope). Acceptable v1 behavior.
5. **[Low — dismissed, not reachable] `InvoiceActions` else-branch labels any non-draft/non-sent status "Paid."** Correct for the real 3-status enum (draft|sent|paid); no current write produces a fourth status.

**Acceptance Auditor verdict:** PASS — all 3 ACs and every non-negotiable (NFR-2 repo isolation, RLS dual-scope on the new column, integer-minor-unit money, AR-14 boundaries, shared `EmailShell`, a11y floor, `InvoiceDocument` reuse, scope discipline — no edit surface / no PDF / no payments) confirmed satisfied.
