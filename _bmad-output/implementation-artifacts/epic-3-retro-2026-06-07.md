## What went well

1. **Heavy, deliberate REUSE — the "what exists vs net-new" front-matter paid for itself every story.** 3.4 found the summarizer already existed (3.1) → it became a quality-bar story, not a rebuild. 3.7 rendered `listPublishedUpdates` (built defensively in 3.6) → a pure UI story. 3.8 was a thin layer over `createCandidate` + `source='manual'`. 3.9 *extracted* the cron's pull so Retry reused it verbatim. Each story's exhaustive code-map (a code-explorer pass before writing the spec) stopped us reinventing wheels.
2. **The privacy boundary is REAL and TESTED, not just asserted.** Publishing is the single grep-verified writer of `state='published'`; the Client read is a projection that never selects `raw_meta` and filters `state='published'`; a **client-ctx test** proves a Client sees only published rows, never candidates. The key insight — *RLS scopes the engagement but NOT candidate-vs-published; the query filter is what hides candidates* — was caught and pinned.
3. **xhigh code-review caught a real bug in nearly every story.** 3.1 record-before-enqueue permanent-drop; 3.2.1 the RLS-update oracle on a foreign-tenant row; 3.3 dead-repo false-success; 3.5 index-based focus re-pointing shortcuts at the wrong row + register-effect churn; 3.6 per-row double-fire showing an error *after* a success; 3.7 the FocusHeading stealing focus on a data change; 3.9 (clean — only hardening). The discipline held for all nine.
4. **Multi-tenant safety was proven, not assumed.** The OAuth-during-install binding (3.2.1) defeats `installation_id` spoofing, validated with a real second freelancer + GitHub account who saw ONLY their own repos.
5. **Defensive landing of security backstops BEFORE the UI** (the Epic-2 habit, continued): `repo_connections` RLS before any connect UI; `listPublishedUpdates` + its privacy test in 3.6 before the 3.7 feed; the `notifications` RLS + FORCE before Epic 4's center.

## What was hard (lessons)

1. **GitHub App registration is browser-only, multi-step, and easy to get subtly wrong.** The Permissions section (Contents/Metadata/Pull requests) is separate from event subscriptions — missing it silently breaks push/PR/release events. **Lesson: external-platform setup needs a checklist + a live ping test, not just "I created it."** (Documented in `docs/github-app-setup.md`.)
2. **The shared App wasn't multi-tenant-safe as first built → an in-epic story (3.2.1).** 3.2's global repo-unique + all-installations listing assumed one freelancer. Making it real required OAuth-during-install + a `github_installations` tenant binding. **Lesson: when an integration is shared infrastructure, model the multi-tenant binding up front — the single-tenant shortcut bought a whole extra story.**
3. **Inngest dev-vs-cloud mode is confusing.** `GET /api/inngest` → 401 in prod is *correct* (cloud-locked); local needs `INNGEST_DEV=1` + the dev server on the right port; a new function needs a **prod re-sync (`PUT /api/inngest`)** — easy to forget (3.6 required it). **Lesson: "added an Inngest function" ⇒ re-sync is a deploy step.**
4. **RLS has sharp edges the policy text hides.** `ship_update_scope`'s WITH CHECK only gates `tenant_id` (a freelancer ctx sets no `app.engagement_id`), so it does NOT block a row stamped to your tenant but pointing at a *foreign* `engagement_id` — which makes the `getEngagement` guard (3.8) genuinely **load-bearing**, not just fail-fast. **Lesson: when the engagement clause is a no-op for the caller, the ownership gate must live in the action.**
5. **Async failure can't reach a synchronous UI.** 3.6's AC wanted a "retry toast on email failure," but the email is an async Inngest step — surfacing its terminal failure to the freelancer's browser needs the push channel **Epic 4** builds. **Lesson: an async fan-out's failures are an async-notification concern; don't promise a sync toast for them.**
6. **Node 26 + tooling friction** (smee-client `UnhandledPromiseRejection`) and **Better Auth `autoSignIn` double verification email** (3.2.1) cost real debugging. **Lesson: pin/guard the dev toolchain; read the auth library's session-policy defaults.**
