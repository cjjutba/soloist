## What went well

1. **The isolation spine scaled flawlessly to multiple tables AND the Client case.** The dual-scope RLS
   predicate (`tenant_id = currentTenant AND (currentEngagement IS NULL OR …)`) was authored once (2.1,
   `engagements`) and reused verbatim for `invitations` (2.3) and `client_access` (2.4). The single
   `isolation.test.ts` grew to cases **(a)–(t)** — every table proved freelancer-scoped, cross-tenant-blocked,
   WITH-CHECK-on-forge, and fail-closed. **Pre-mortem guardrail #5** (a client scoped to E1 can never see E2)
   was satisfied in 2.1 *before any client UI* and validated again in 2.4.
2. **The xhigh code-review caught the epic's most dangerous bug — pre-production, again.** 2.3's
   `resendInviteAction` could silently **un-accept an active client and re-mint an account-takeover token**
   (the UI hid the button, but the server action was directly callable). Also: 2.4's `createAccount`-orphan
   that permanently blocked retries + the TOCTOU single-use hole (fixed with an atomic conditional stamp);
   2.6's a11y focus regression. Every story surfaced a real fix.
3. **The pre-auth RLS-bypass (2.4) was a deliberate, documented design, not an accident.** The token-hash
   invitation lookup + the `ClientAccess` scope-bootstrap are the ONE sanctioned bypass — keyed on an
   unguessable hash / the session's own userId, heavily commented as such. The Better Auth internal-adapter
   API (`auth.$context.internalAdapter.createUser/createAccount`) was verified against the installed dist
   *before* building the "create a verified client with no verification email" path.
4. **Route groups gave clean surface separation, reused twice.** `(detail)` (cockpit engagement shell) and
   `(shell)` (portal) kept the full-screen surfaces (the edit form / the onboarding hero) out of the wrong
   chrome — the same idiom both times.
5. **Steady velocity with the full BMad chain.** 6 stories, all gates green every time, in one working session.

## What was hard (lessons)

1. **Auth-library behavior needs source/dist verification (reinforced from Epic 1).** Better Auth's internal
   adapter is undocumented; the no-verification-email accept path required reading the dist. **Lesson: for
   auth/security-adjacent library behavior, verify at the source/dist, not the docs.**
2. **a11y on HAND-ROLLED interactive/focus components is a recurring review-catch.** `autoFocus` on a server
   `<h1>` doesn't focus (2.5); a persistent layout meant `FocusHeading` didn't re-fire on in-shell nav (2.6);
   the hand-rolled portal nav lacked focus rings + Esc focus-return (2.6). The shared `Field`/`Button` bake
   a11y in; bespoke controls don't. **Lesson: hand-rolled focusable UI needs explicit focus management +
   visible focus rings, reviewed every time.**
3. **Read fan-out from per-request guards.** `getAppSession` is intentionally not `cache()`-wrapped, so portal
   pages re-resolve the session 2–3× and duplicate `getTenant`/`getBranding`. Flagged in every portal review.
4. **Stale `.next/types` after route-file moves.** Moving pages into `(shell)`/`(detail)` left a phantom
   typecheck error until a rebuild regenerated the route types. **Lesson: rebuild after moving route files.**

## Significant discovery for Epic 3 planning

**No architectural rework — the plan holds.** The data layer, Inngest, and the GitHub App model were all
anticipated. **BUT Epic 3 is the riskiest epic so far** and has real EXTERNAL-SETUP prerequisites that block
Story 3.1 (a deliberate "moat spike" to de-risk exactly this):

1. **Register a GitHub App** (CJ) — least-privilege read-only (`contents`/`metadata`/`pull_requests` + the
   `push`/`pull_request`/`release` webhook events). Provides `GITHUB_APP_ID`, the private key, the webhook
   secret, and client id/secret → set as Vercel + `.env.local` secrets. **This is the #1 blocker — 3.1's
   webhook path cannot be completed without it.**
2. **A local-dev webhook tunnel + the Inngest dev server** — to test the `/api/webhooks/github` → Inngest →
   candidate path locally before deploying.
3. **`INNGEST_*` env** (event + signing keys; Inngest cloud or the dev server).
4. **The Epic-1 ops** become pressing: **push the repo to GitHub** (webhooks/CI want it there) and set the
   Sentry DSN.

New surface in Epic 3: `webhook_events`, `repo_connections`, `ship_updates` tables (RLS-scoped); Octokit
(already a dep); the poll feed `GET /api/feed/[engagementId]`.
